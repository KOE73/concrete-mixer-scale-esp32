## Краткое резюме

Задача: сделать весовую подставку под бытовую бетономешалку на **N тензодатчиках**, 
с передачей данных по **Wi-Fi** на ПК и анализом в C#. 

Количество датчиков может быть N, но в примеры основанны на 3 датчиках.

Главный вывод: в этой системе не надо мыслить как в статических весах. 
Бетономешалка крутится, нагрузка гуляет, отдельные датчики постоянно перераспределяются. 
Поэтому рабочая модель — **виртуальный датчик**:

raw1/raw2/raw3
- rawSum
- удаление цифровых глюков
- cleanSum
- MA1/MA3/MA5/MA10
- zero по пустой крутящейся мешалке
- рабочие попугаи / условные кг / контрольные точки

## Проблемы

### 1. Динамическая нагрузка

Барабан вращается, смесь перекатывается, рама вибрирует. Индивидуальный offset каждого датчика хорош для статических весов, но здесь отдельный канал сам по себе малоинформативен.

Вывод: управление делать не по отдельным каналам, а по суммарному виртуальному сигналу.

---

### 2. Останавливать бетономешалку с грузом нельзя

Значит вся логика должна работать при вращении. Нельзя строить алгоритм вокруг “остановил → дождался стабильности → измерил”.

Вывод: zero, контрольные точки и текущий вес должны сниматься в том же режиме, в котором идёт работа: **пустая мешалка крутится → zero**, загруженная мешалка крутится → измерение.

---

### 3. Есть одиночные цифровые выбросы

По графикам видно, что выбросы не похожи на физику. Это одиночные пики в миллионы вверх/вниз, иногда около пределов 24-битного signed диапазона.

Вероятные причины:

```text
битовый срыв чтения HX711/АЦП
чтение не по ready
ошибка sign extension
Wi-Fi/interrupt во время bit-bang чтения
помехи по питанию/земле
длинные провода SCK/DOUT
плохой контакт
```

Вывод: такие значения надо не сглаживать, а **выкидывать до MA**.

---

### 4. Небольшие одиночные отклонения можно не трогать

При 10 SPS:

```text
MA1  = 10 значений
MA3  = 30
MA5  = 50
MA10 = 100
```

Один небольшой выпад почти не влияет на MA10 и сам исчезает через 10 секунд.

Вывод: фильтр должен ловить только **физически невозможные** скачки. Не надо строить сложный soft/pending/median-фильтр.

---

### 5. Рецепт не фиксированный

Последовательность загрузки может меняться. Обычно:

```text
вода примерно 60%
щебень весь
остаток воды
цемент примерно полмешка
песок
```

Но это не должно быть жёстко зашито.

Вывод: нужна не модель “рецепта”, а массив **контрольных точек** до 16 штук.

---

## Решения

### 1. Разделить программы

Сделать две отдельные программы:

```text
MixerScale.Logger
  принимает UDP
  пишет CSV
  ничего умного не анализирует

MixerScale.Analyzer
  открывает CSV
  рисует графики
  подбирает фильтры
  показывает rawSum/cleanSum/MA
  помогает выбрать параметры
```

Позже можно добавить live controller, но сначала важнее надёжные логи.

---

### 2. ESP32 шлёт данные по Wi-Fi

Пакет от ESP32:

```text
seq,ms,raw1,raw2,raw3,rawSum,cleanSum,ma1,ma3,ma5,ma10,flags
```

`raw1/raw2/raw3` обязательно сохранять, даже если управление идёт по сумме. Они нужны для диагностики, чтобы увидеть, какой канал улетает.

---

### 3. Фильтр выбросов

Алгоритм простой:

```text
есть lastGoodSum
пришёл rawSum

если скачок от lastGoodSum явно невозможный:
    cleanSum = lastGoodSum
    ставим флаг GLITCH
    в MA кладём lastGoodSum

иначе:
    cleanSum = rawSum
    lastGoodSum = rawSum
    в MA кладём cleanSum
```

Не использовать median, soft limit, pending-подтверждение. Только hard reject.

Порог сделать настраиваемым. Начать примерно с:

```text
hardDelta = 500 000 ... 1 000 000 raw units
```

Потом уточнить по реальным логам работающей мешалки.

---

### 4. MA считать по cleanSum

`rawSum` нужен для лога.
`cleanSum` — вход в MA.

MA окна:

```text
MA1  = 1 секунда
MA3  = 3 секунды
MA5  = 5 секунд
MA10 = 10 секунд
```

При 10 SPS достаточно кольцевого буфера на 100 значений.

---

### 5. Zero делать после MA

Zero не индивидуальный по датчикам. Zero — это базовый уровень виртуального датчика в рабочем режиме.

Практически:

```text
пустая мешалка крутится
жмём ZERO
берём MA10 как ноль
```

Дальше текущий рабочий сигнал:

```text
MA5 или MA10 относительно этого zero
```

---

### 6. Контрольные точки

Сделать массив максимум на 16 точек.

Режим обучения:

```text
пустой барабан → ZERO
налил первую воду → SAVE POINT
засыпал щебень → SAVE POINT
долил воду → SAVE POINT
цемент → SAVE POINT
песок → SAVE POINT
сохранил профиль
```

Сохранять не рецепт, а контрольные значения:

```text
point[0]
point[1]
point[2]
...
```

Единицы хранения — рабочие условные единицы после MA/zero. Можно отображать как условные кг, но не считать их лабораторными килограммами.

---

## Подробный план действий для агента

```text
Цель:
Разработать C#-решение для логирования и анализа сигналов весовой подставки под бытовую бетономешалку на 3 тензодатчиках. Данные приходят от ESP32 по Wi-Fi/UDP. Основная задача — получить устойчивый виртуальный весовой сигнал из raw1/raw2/raw3 в условиях вращающейся бетономешалки и цифровых выбросов.

Архитектура solution:

src/
  MixerScale.Protocol/
    Общие DTO.
    Парсер UDP-пакетов.
    Модель строки CSV.
    Общие flags.
    Общие настройки фильтра.

  MixerScale.Logger.Console/
    UDP-приёмник.
    Запись CSV.
    Счётчик потерь seq.
    Горячие клавиши событий.
    Никакой сложной математики.

  MixerScale.Analyzer.Avalonia/
    Открытие CSV.
    Графики raw1/raw2/raw3/rawSum/cleanSum/MA.
    Отображение flags/glitches/events.
    Настройка hardDelta.
    Пересчёт cleanSum и MA по CSV.
    Сохранение вариантов настроек анализа.

Формат UDP-пакета:
  seq,ms,raw1,raw2,raw3,rawSum,cleanSum,ma1,ma3,ma5,ma10,flags

Logger должен писать CSV с полями:
  pc_time_iso
  pc_elapsed_ms
  remote_ip
  seq
  device_ms
  raw1
  raw2
  raw3
  rawSum
  cleanSum
  ma1
  ma3
  ma5
  ma10
  flags
  lost_total
  event
  original_packet

Logger не должен:
  сглаживать данные
  исправлять raw
  пересчитывать историю
  скрывать ошибки парсинга

Analyzer должен уметь:
  открыть CSV
  построить rawSum
  построить cleanSum
  построить MA1/MA3/MA5/MA10
  показать выбросы
  показать, какие сэмплы были заменены lastGood
  дать поменять hardDelta и пересчитать график
  сохранить настройки анализа

Алгоритм обработки сигнала:
  1. Использовать raw1/raw2/raw3 как диагностические каналы.
  2. Основной рабочий канал — rawSum.
  3. Перед MA применить hard-glitch reject.
  4. Если rawSum отличается от lastGoodSum сильнее hardDelta:
       cleanSum = lastGoodSum
       поставить флаг GLITCH_DROPPED
       в MA положить lastGoodSum
     Иначе:
       cleanSum = rawSum
       lastGoodSum = rawSum
       в MA положить cleanSum
  5. MA считать только по cleanSum.
  6. Малые одиночные отклонения не удалять — MA их сама погасит.
  7. Hard-фильтр предназначен только для цифрового мусора в миллионы raw units.

Начальные настройки:
  sampleRateHz = 10
  ma1Window = 10
  ma3Window = 30
  ma5Window = 50
  ma10Window = 100
  hardDelta = configurable, default 500000
  maxPoints = 16

Логика zero:
  ZERO выполняется на пустой крутящейся мешалке.
  В качестве нуля использовать MA10.
  Не делать индивидуальный offset каждого датчика как основную рабочую модель.
  Не делать auto-zero во время замеса.

Логика контрольных точек:
  Сделать Teach Mode.
  В Teach Mode пользователь:
    ZERO
    SAVE POINT после каждого технологического этапа загрузки
  SAVE POINT сохраняет текущее значение рабочего сигнала относительно zero.
  Максимум 16 точек.
  Точки не привязаны к материалам.
  Note/label опциональны.

Run Mode:
  Загрузить профиль контрольных точек.
  Сделать ZERO на пустой крутящейся мешалке.
  Текущий рабочий сигнал брать по MA5 или MA10 относительно zero.
  Определять следующую контрольную точку.
  Показывать:
    текущая точка
    текущее значение
    цель
    осталось
    состояние: далеко / медленно / попал / перелёт

Важно:
  Не усложнять фильтр.
  Не использовать median на первом этапе.
  Не использовать soft/pending-подтверждение.
  Не пытаться вычищать физическую динамику бетономешалки.
  Удалять только явно невозможные цифровые выбросы.
  Все raw-данные сохранять для последующего анализа.
```

## Главный итог

Правильная модель для этой задачи:

```text
не "три статических весовых датчика",
а "один виртуальный динамический датчик с защитой от цифровых глюков"
```

Сначала надо собрать реальные логи, подобрать `hardDelta`, убедиться, что `cleanSum` не пускает пики в MA, и только потом делать удобное управление по контрольным точкам.
