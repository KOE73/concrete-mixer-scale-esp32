# UDP CSV contract

Этот документ является центральным описанием CSV-формата для сырой UDP-телеметрии весов. Прошивка, UDP-приемник, анализатор и будущие анализаторы должны опираться на него, а не заводить локальные варианты формата.

## Назначение

Один UDP-пакет равен одной CSV-строке и описывает один измеренный сэмпл. UDP выбран как поток реального времени: пакет отправляется один раз, без подтверждения и без повтора. Если пакет потерян сетью или приемником, следующий сэмпл все равно идет дальше с новым `seq`.

Основные следствия:

- `seq` является номером измерения, а не номером успешной записи в файл.
- Потери UDP определяются по пропускам `seq` внутри одного `scale_id`.
- Приемник не должен ждать повторов старых пакетов.
- Файл CSV является журналом того, что реально дошло до приемника.

## Строка

```csv
scale_id,seq,ms,raw1,raw2,raw3,raw_sum,kg_sum,flags[,win1,ma1,win2,ma2,...]
```

Количество `rawN` не фиксируется в бизнес-логике. Оно должно соответствовать количеству каналов тензодатчиков в конфигурации прошивки.
После поля `flags` могут следовать необязательные пары `winK,maK`, где `winK` — размер окна скользящего среднего в секундах, а `maK` — рассчитанное значение скользящего среднего (в кг) для этого окна.


## Поля

| Поле | Обязательно | Тип | Описание | Причина | Следствие |
| --- | --- | --- | --- | --- | --- |
| `scale_id` | Да | uint32, больше 0 | Числовой идентификатор весов. По умолчанию `1`. | В одной сети может быть несколько весов. | Приемник раскладывает файлы по подпапкам `C:\ScaleData\<scale_id>\`. Анализатор сначала выбирает папку весов, потом CSV-файл. |
| `seq` | Да | uint64 | Номер измерения, увеличивается при создании сэмпла в прошивке. | Нужен контроль потерь UDP и разрывов потока. | Пропуски `seq` означают потерянные или не записанные пакеты. Повторный `seq` должен считаться дубликатом/аномалией, а не новым измерением. |
| `ms` | Да | uint64 | Время ESP32 в миллисекундах для этого сэмпла. | Нужна временная ось без зависимости от часов ПК. | Для графиков и анализа использовать `ms`; время записи файла отражает прием на ПК и может отличаться. |
| `raw1..rawN` | Да | int32/int64 | Полный сырой сигнал каждого HX711-канала в порядке конфигурации каналов прошивки. | Сырые данные нужны для диагностики датчиков, калибровки, фильтров и будущих анализаторов. | Анализаторы не должны предполагать ровно 3 канала; число raw-полей определяется строкой. |
| `raw_sum` | Да | int64 | Сумма всех `rawN` в этой строке. | Быстрая проверка целостности и общий сырой тренд без пересчета каналов. | Если `raw_sum` не равен сумме `rawN`, строка подозрительная: ошибка формата, обрезка или несовместимость версии. |
| `kg_sum` | Да | float, invariant culture | Текущий расчет веса на ESP32 для контроля. | Позволяет сравнить расчет прошивки с расчетом анализаторов. | Расхождение с офлайн-расчетом может означать разные коэффициенты, фильтры, тару или ошибку в анализаторе. |
| `flags` | Да | строка без запятых | Состояние сэмпла: валидность, ошибка датчика и будущие состояния вроде мотор/тара. Текущие значения: `valid`, `invalid|sensor_error`. | Нужна диагностика без разбора отдельных внутренних структур прошивки. | Анализаторы должны сохранять неизвестные флаги как есть и не падать при добавлении новых значений. |

## Совместимость

- Новые поля лучше добавлять в конец строки после `flags`, если это не ломает существующие приемники. Если поле становится обязательным для всех программ, сначала обновить этот документ.
- Нельзя менять смысл существующего поля без явного изменения контракта и миграции приемника/анализатора.
- Разделитель CSV - запятая. Числа пишутся в invariant culture: десятичная точка, без локальных запятых.
- `flags` сейчас не должен содержать запятые. Если понадобятся значения с запятыми, приемники должны перейти на полноценный CSV-парсер до изменения прошивки.

## Файлы приемника

По умолчанию UDP-приемник слушает порт `4222` и пишет данные в `C:\ScaleData`.

Структура хранения:

```text
C:\ScaleData\<scale_id>\scale-raw-YYYYMMDD-HHMMSS.csv
```

Новые сессии пишутся в новые файлы. Старые файлы не удаляются и не ротируются. Потеря UDP-пакета не компенсируется повторной отправкой: это намеренное свойство real-time потока, а не ошибка приемника.
